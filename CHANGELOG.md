### 21.10.2026

### Инкрементальное дерево в подокне тригклина (21.10, ночь 3)

Дерево «Чистки триггеров» теперь наполняется ПО ХОДУ скана, а не разом
в конце:

- `stage_triggers.py --scan` после каждого шага печатает маркеры
  `@@TRIG <json>`: пустые папки/txt, отключённые, глобалки; мёртвые
  функции идут кусками по 1000 записей (одна мегабайтная json-строка
  тормозила парсер). Маркеры в журнал не попадают (как `@@TICK`),
  итоговый `triggers_scan.json` не изменился.
- `_run_streamed` принял параметр `on_line`: вернула True, значит строка
  поглощена коллбэком и не идёт в журнал. Скан тригклина передаёт
  обработчик маркеров: клиентский филлер `_trigclean_fill` вливает
  строки в дерево налету через `_safe_after`.
- Вставка строк вынесена в общий `_trigclean_add` (show и филлер).
  Финальный показ при уже наполненном дереве (`filled`) не дублирует
  вставки: только сверный счётчик и копит итог для «Удалить».
- Тесты `test_trigfill.py` (CLI маркеры == итог; GUI-поток вливает
  строки, show без дублей), регресс streamed/gui windows/trig opt
  пролезает. Нюанс, замеченный тестом: `after()` из фонового потока
  доходит до UI только при работающем mainloop, в проде это так
  всегда.

### Аудит

Полный разбор пайплайна и GUI, отчёт `docs/audit-2026-10-20.md`.
Исправления разбиты на два батча: этапы и интерфейс.

### Перенос и этапы

- Галочки этапов из окна действительно управляют прогоном: `stage_enabled`
  читает `cfg['stage_enabled']`, для именованных профилей список профиля
  пересекается с галочками. Неизвестный `--stage` отклоняется с подсказкой.
- Режим «Заменять стандарт» доведён до записи: `stage_tables` применяет
  `replace_std.json` к существующим секциям приёмника. Блочные поля `[=[`
  намеренно не переносятся. Пути из `assets_renames` подставляются в таблицы
  с учётом удвоенных `\\` в `ini`.
- Починка таблиц больше не ломает валидный `_parent`, объявленный ниже
  по файлу: два прохода, сначала собираются все ID. Прошлый бэкап починки
  не затирается.
- «Чистка триггеров» чистит ту карту, что указана в окне (`--dir`),
  в подтверждении виден путь. Заметки `.txt` сохраняются при
  `del_notes=False`, второй проход пустых папок учитывает `exclude_dirs`.
- Конвертер равкодов: CLI `--reverse` больше не падает с NameError,
  hex-режим конвертирует только 4 печатных ASCII-байта.
- `globals` и вырезка кода находят нумерованную запись каталога без кавычек
  (`213-dep:`), файл больше не уезжает рядом с папкой. Свой прошлый
  Globals-файл исключается из поиска.
- Пустая `war3map.doo` и отсутствие `war3mapUnits.doo`/`w3e` не роняют
  геометрию.
- `stage_import` не режет `imp.ini` при отсутствии `}`; `stage_verify`
  не дублирует поиск `prebuilt` и показывает настоящий номер строки.
- Логи и бэкапы чистки, починки и равкодов пишутся рядом с конфигом,
  `load_std_ids` в чистке и починке читает конфиг запуска, а не общий.

### Интерфейс

- Скан чистки, удаление, починка таблиц и манифест выполняются в фоне,
  окно не замирает; результат возвращается в главный поток.
- Закрытие окна во время прогона спрашивает подтверждение и убивает
  дерево процессов. Кнопка «Стоп» тоже валит дочерние этапы.
- «Полный цикл» учитывает Dry-run.
- Конвертер равкодов: `last_mode` хранится базовым (`both/hex/dec/jhex`),
  при повторном открытии радиокнопка снова выбрана; ошибка конвертации
  всегда попадает в журнал.
- Окно чистки триггеров читает `triggers_scan.json` рядом с конфигом.
- Литеральные `\n` в подсказках защитного списка исправлены.
- `after()` из рабочих потоков защищён от закрытого окна; деобфускация
  и манифест запускаются без мелькания консоли.
- Главное окно считается от фактического экрана: на 1920x1080 нижний
  край со статусбаром больше не уезжает за экран, минимальный размер
  прижат к рабочей области.

### Таймаут, пульс и пути чисток (21.10, поздний вечер)

По факту прогонов: защита на 15 минут убивала рабочий этап на большой
карте, полоска прогресса стояла на 75% без признаков жизни, а state не
показывал, где именно процесс остановлен.

- Лимит этапа настраивается: `safety.stage_timeout_min` в минутах,
  0 = ждать без лимита. В GUI это поле «Лимит этапа, мин» в колонке
  опций. В рабочем конфиге поставлено 60 минут вместо прежних жёстких
  15. Таймаут больше не бросает исключение посреди коммуникации:
  этап запускается через `Popen`, при превышении процесс этапа
  останавливается по таймеру, этап помечается как упавший.
- Пульс: оркестратор каждые 20 секунд выдаёт маркер `@@TICK <сек>`
  (в журнал не пишется). GUI показывает в статусе «этап X идёт N сек»,
  поэтому длинный этап geometry больше не выглядит зависшим. Полоска
  по-прежнему двигается по этапам, а не внутри одного этапа.
- State теперь пишется и ПЕРЕД этапом (`last_stage`, `last_stage_ts`),
  а не только после успеха: по `--status` видно, на каком этапе процесс
  убило, даже если этап не завершился.
- Пути инструментов чистки приведены к консистентности с пайплайном
  и настраиваются рядом с конфигом:
  чистка карты `cleanup.log_dir` / `cleanup.backup_dir`,
  чистка триггеров `trigclean.log_dir` / `trigclean.backup_dir`,
  починка таблиц `repair.log_dir` / `repair.backup_dir`,
  конвертер равкодов `rawconv.backup_dir` (в CLI флаг `--backup-dir`).
  Без настроек дефолт прежний: `logs/` и `transfer_backup/...`
  у конфига. GUI и CLI читают одни и те же ключи.
- Прочее: журнал переноса тоже уважает общий `log_dir` из конфига.

Проверка: `py_compile` изменённых файлов; временные тесты таймаута
(этап без лимита проходит, этап с лимитом 0.05 мин убивается за ~3 сек
с сообщением «ПРЕВЫШЕН ЛИМИТ»), пульса `@@TICK` в статусе GUI,
`state.last_stage` до этапа и его показа в `--status`; регресс
отката импорта и окон GUI. Лог-примеры с падениями `stage_deps`/
`stage_tables` от 17.09 в текущем коде не воспроизводятся (те правки
давно в репозитории).

### Скорость сканов и живой вывод инструментов (21.10, ночь)

По наблюдениям: скан триггеров молчал по 10-15 минут, а подокна
инструментов показывали статичное «скан идёт...» без признаков жизни.

Ускорение (главная причина молчания была в производительности):

- Поиск UNUSED-глобалок был O(имена x весь текст карты): сотни
  `re.search` по мегабайтному тексту. Стал один проход `re.findall`
  + проверка вхождения в множество. Результат тот же, минуты
  превращаются в секунды.
- Каскад мёртвых функций перечитывал все .j файлы на каждой итерации;
  теперь тексты читаются один раз (общий кэш).

Живой вывод (где тишина остаётся, там теперь видно движение):

- GUI: построчный стрим `_run_streamed` вместо `subprocess.run` в
  чистке триггеров (скан/удаление/ДЕМО), манифесте и деобфускации:
  вывод этапа идёт в журнал строка за строкой, пока работает.
- Скан триггеров печатает шаги и счётчики (файлы кода, функции,
  отключённые, глобалки, мёртвые) с хартбитами каждые 100 файлов.
- Чистка карты (встроенный скан/удаление) и починка таблиц получают
  прогресс-сообщения шагов («проход 1: ability (секций 2030)...»,
  «таблица unit...»), GUI показывает их в надписи окна.
- Подокна: секундный счётчик «скан идёт: N сек...» в надписи, пока
  инструмент работает.

Проверка: `py_compile`; временные тесты: скан триггеров печатает шаги,
прогресс-коллбэки scan/delete/repair вызываются, стрим `_run_streamed`
кладёт строки и теги в журнал; регресс подокон GUI. Крэш-лога нет.

### Замеры и второй круг оптимизации (21.10, ночь 2)

Профилирование на реальной приёмнике LOWSTOBVO (~9 МБ таблиц, 2021
.j файл):

- Скан триггеров: был ~29 сек с хартбитами (до оптимизаций: минуты);
  нашёл главный остаток: сбор текста карты через `all_code += файл`
  в цикле был квадратичным (18.7 сек на scan_globals). Стал список
  + `join`: 18.7 → 1.21 сек, весь скан 29 → 9.4 сек.
- Чистка карты: регексы построчного разбора вынесены в
  предкомпилированные (`_RX_SECTION`, `_RX_FIELD`), 750 тыс. вызовов
  больше не ходят через кэш компиляции re: 4.15 → 2.09 сек.
  Результат идентичен baseline (suffix 33, badcode 1, unused 1453,
  каскад-волна 1).
- Замеры прочего: починка 3.6 сек, деобфускация war3map.j (3.9 МБ)
  12 сек (VERIFY: OK), манифест 0.8 сек, полный пайплайн dry-run
  5.5 сек. Всё остальное уже не бутылочное горлышко.

Общий итог дня по «тишине»: сканы из минут и "+" секунд, где
долгое, там теперь видно шаги и счётчики.

Примечание для себя пользователя: в logs/transfer.log есть
синтетические строки от проверок таймаута (22:43, «ПРЕВЫШЕН ЛИМИТ
0.05 мин») и запись двойного verify 22:39: это тестовый шум, а не
реальный прогон; можно отрезать при желании.

### Отложено

Осознанно не в этом батче: откат не удаляет созданные этапом файлы
(у импорта нет снапшота), повторный перенос не обновляет существующие
секции, прогресс-бар парсит русские строки, tooltip на `CTkFrame`,
`import.enabled`/`code.enabled` только через файл, `transfer_gui.py`
устарел.

### Доработка после аудита (21.10, вечер)

Перечисленные выше отложенные пункты закрыты.

- Откат импорта: перед этапом снимается снапшот `table/imp.ini`,
  `stage_import` ведёт `import_created.txt`. Откат возвращает `imp.ini`,
  а созданные импортом ассеты переносит в
  `transfer_backup/rollback_import_<метка>`, ничего не удаляя. Прошлый
  список созданных файлов перед перезаписью копируется в
  `transfer_backup/import_created_<метка>.txt`.
- `stage_import` при отсутствии `deps_result.json` завершается ошибкой,
  а не «успешным» no-op: иначе оркестратор записал бы `import` последним
  этапом и откат взял бы чужой список созданных файлов.
- Прошлый бэкап этапа больше не удаляется: при новом снапшоте он
  переносится в `transfer_backup/_old/<этап>_<метка>`.
- Повторный перенос: опция `tables_update_existing` и галочка
  «Обновлять существующие объекты (поля донора поверх приёмника)».
  Простые поля донора обновляют существующую секцию, блочные
  `[=[ ... ]=]` и поля, которых нет у донора, не трогаются. Пути
  `assets_renames` применяются и к полям `replace_std`.
- Прогресс: оркестратор печатает машинные маркеры `@@PROGRESS` и
  `@@STAGE`, GUI читает только их; русские формулировки этапов больше
  не влияют на полоску, маркеры не пишутся в журнал.
- `stage_code`: GUI-пары без `.j` попадают в `catalog.lml`; равкод,
  который в разных типах получил разные ID, не заменяется наугад,
  а выводится предупреждением.
- `stage_mapping`: `mapping_pair.json` привязывает KEEP к паре карт.
  При смене пары или `--remap` старый маппинг уходит в
  `transfer_backup/mapping_<метка>`, `replace_std.json` перезаписывается
  всегда (пустой тоже), чтобы не применялись поля прошлого донора.
  Если `mapping_pair.json` ещё нет (обновление со старой версии),
  прежний маппинг сохраняется, привязка записывается при первом прогоне.
- `import.enabled`/`code.enabled` синхронизируются с галочками этапов
  при сохранении конфига.
- Мелочи: мёртвый черновик в `read_w3e_heights` закомментирован,
  `parse_bodies` сохраняет строку открытия `[=[`, tooltip работает на
  `CTkFrame`, эмотикон в README заменён на «Важно:», импорт печатает
  прогресс каждые 200 файлов.
- `transfer_gui.py` не удалён: старый файл оставлен на месте, пока
  пользователь не решит иначе.

Проверка: `py_compile` изменённых файлов, временные тесты импорта и
отката, обновления существующих секций, смены пары карт, GUI-пар без
`.j`, чтения W3E и `parse_bodies`. GUI и подокна «Чистка карты»,
«Перенос триггеров» открываются, tooltip на `CTkFrame` показывается,
`logs/gui_crash.log` не появился.

## 20.10.2026

### Перенос

- Раскладка папок триггеров: новый режим «Папки как у донора». Каждая папка
  триггеров донора получает свою папку верхнего уровня в `trigger\` приёмника,
  имена сохраняются 1:1, структура видна в редакторе триггеров. Старый режим
  «Одна папка» работает как раньше, переключение чистит старую раскладку
  по манифесту деплоя.
- Фикс повторных прогонов: ключи `catalog.lml` пишутся и читаются одинаково
  в обоих форматах (с кавычками и без), секции больше не «переезжают» между
  файлами при повторных запусках.

### Интерфейс

- Исправлен фильтр вывода по режиму: в «Обслуживании» вывод сервисных кнопок
  больше не пропадает из журнала (проверка scope сравнивала не то).
- Окно «Триггеры...»: выбор папок больше не теряется при сохранении конфига
  (раньше переносилось всё, независимо от выбранных); после разового переноса
  ограничение снимается само, обычный прогон не остаётся урезанным.
- Окно «Чистка»: скан не падает при первом открытии, защитный список
  `cleanup_protect.json` учитывается с первого раза; фильтр сбрасывается
  при каждом открытии окна.
- Галочки этапов восстанавливаются из конфига при запуске (публиковались
  в конфиг, но никогда оттуда не читались).
- Отключение «Обновлять catalog.lml» действительно сохраняется и работает.
- Деобфускация: поле «Файл .j» сразу подставляет `war3map.j` карты из конфига.
- Окно «Чистка триггеров»: удаление пустых txt сопоставляется по полному
  пути, а не по имени файла (при одинаковом имени в разных папках удалялась
  первая попавшаяся).
- Кнопка «Стоп» в строке состояния: прерывание зависшего прогона.
- Прогресс: чипы этапов обновляются после каждого этапа, а не только в конце
  прогона; ложная покраска строк журнала по «код 1» убрана; баннер режима
  «Обслуживание» восстанавливается после прогона.
- Окно приложения не открывается вне видимой области (координаты из конфига
  прижимаются к текущему экрану), минимальная ширина поднята до 1264 пикселя
  для масштаба 125%.
- Краш запуска на customtkinter 6.0 (Tooltip на перестроенных сегментах)
  исправлен, запуск проверен вживую.

### Журналы и состояние

- Журнал прогона ведётся отдельно по каждому конфигу: `transfer.log` для
  `transfer_config.json`, `<имя конфига>.log` для остальных, в `logs\` рядом
  с конфигом. Сессии разных конфигов больше не подмешиваются друг в друга.
- Журнал в окне очищается при каждом новом прогоне, история на диске
  сохраняется. «Журнал» и «Манифест» открывают файлы текущего конфига.
- state-файл берётся из конфига (`safety.state_file`) и читается рядом
  с конфигом, не с папкой скриптов.
- Дочерние процессы запускаются с `PYTHONUTF8=1`, консоль не мигает
  под pythonw (CREATE_NO_WINDOW).

### Запуск

- «Утилита переноса.bat» через py-запускатор сначала пробует закреплённый
  `pyw -3.14` (полный набор пакетов), затем py-дефолт, затем `python` из PATH;
  на машинах с несколькими Python выбирается рабочий интерпретатор.
- Отсутствие customtkinter в не том Python больше не умирает молча: выводится
  окно с причиной, пишется `logs\gui_crash.log` (раньше под pythonw, без
  консоли, падение не оставляло следов).
- Ошибка отсутствия конфига в CLI заменяет трейсбек краткой подсказкой;
  GUI при первом запуске сам создаёт конфиг по умолчанию.
- Служебные `bat`-файлы всегда пишутся с CRLF, закреплено в `.gitattributes`
  (cmd с LF не работает).
