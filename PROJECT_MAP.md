# Карта программы Wc3Transfer

Метафайл для входа в проект: что есть, какой файл за что отвечает, как
запускается. Актуально на 22.10.2026. Подробности по этапам и конвенциям
— в `README.md`, `DEVELOPMENT.md`, `CHANGELOG.md` (история правок).

## Назначение

Перенос содержимого между картами Warcraft 3 в lni-формате (w3x2lni):
объекты (юниты/способности/предметы/бафы/апгрейды), код (.j), GUI- и
текстовые триггеры (.lml/.txt), импорт ассетов, геометрия (декор/юниты),
тестовые спавны. Плюс обслуживание одной карты: чистка, починка таблиц,
деобфускация JASS, конверт равкодов.

Директории карт с парой (донор/приёмник) задаются в конфиге; карты лежат
вне репозитория, например `C:\AgentLetta\BVO3.2\` (донор) и
`C:\AgentLetta\LOWSTOBVO\` (приёмник), с подпапками `table/`, `trigger/`,
`map/`, `unit/` (lni-раскладка w3x2lni).

## Вход и запуск

| Как | Что |
| --- | --- |
| `Утилита переноса.bat` | Лаунчер GUI (`pyw -3.14`, pythonw). Ошибки старта: `logs/gui_crash.log` |
| `python transfer_run.py --all` | Весь пайплайн без GUI; `--plan`, `--dry-run`, `--stage X`, `--loop`, `--rollback`, `--status`, `--reset`, `--remap` |
| `python stage_<имя>.py <конфиг>` | Одиночный этап с конфигом в аргументе |

- Интерпретатор пинить: `py -3.14` (на машине также есть пустой 3.15).
- Один фоновый прогон за раз; запуск с `python -u` и редиректом в лог.
- Журналы и state пишутся РЯДОМ С КОНФИГОМ (`logs/transfer.log` для
  `transfer_config.json`; `<имя>.log` для остальных конфигов).

## Конфиги и данные рядом с конфигом

| Файл | Роль |
| --- | --- |
| `transfer_config.json` | Основной конфиг (пары карт, этапы, таблицы, префиксы, раскладка кода). НЕ заменять на example |
| `transfer_config_set.json` | Личный набор выборочного переноса (include/exclude) рядом с конфигом |
| `transfer_set.json` / `transfer_set.example.json` | Формат набора выбора: исключения объектов/триггеров |
| `transfer_state.json` | Прогресс этапов (докатка пропускает пройденное) |
| `transfer_mapping.json` / `.pkl` | Маппинг ID донор → приёмник |
| `target_id_registry.json` | Реестр занятых ID приёмника |
| `deps_result.json` | Рассчитанные зависимости (герои и их скиллы и пр.) |
| `deploy_manifest.json` | Что утилита записала в приёмник («поколения» деплоя); на его основе 下面 чистятся старые записи |
| `import_created.txt`, `mapping_pair.json`, `replace_std.json` | Рабочие файлы этапов (импорт, пара карт, замены стандартных полей) |
| `std_ids.json` | Служебный справочник стандартных ID (в корне, трекнут) |
| `template/` | Пребылд-таблицы w3x2lni (Custom/Melee, 32 МБ) — нужны этапу tables |
| `logs/` | Журналы прогонов и этапов |
| `transfer_backup/` | Бэкапы при возвратах |
| `archive/old_gui_22.10/` | Старая GUI (до CustomTkinter) |
| `test/` | Одноразовые диагностические/патчевые скрипты прошлых сессий и их артефакты; в гит-игноре, не часть пайплайна |
| `docs/` | Локальные заметки разработки, вне гита |

## Ядро пайплайна (трекнутые скрипты)

| Файл | За что отвечает |
| --- | --- |
| `transfer_run.py` | Оркестратор: порядок этапов, дока/пропуски по state, лимит времени на этап, rollback/reset/plan |
| `transfer_gui_ctk.py` | GUI (CustomTkinter): конфиги, галочки этапов, пресеты настроек, запуск пайплайна, просмотр логов |
| `transfer_set.py` | Загрузчик набора выборочного переноса (include/exclude objects/triggers), соединяет конфиг и `_set.json` |

## Этапы (stage_*.py), порядок: mapping → registry → deps → tables → import → code → code_cut → globals → geometry → testspawn → verify

| Этап | За что отвечает |
| --- | --- |
| `stage_mapping.py` | Маппинг объектов донора на свободные ID приёмника |
| `stage_registry.py` | Пересчёт реестра занятых ID приёмника |
| `stage_deps.py` | Зависимости: какие герои/юниты/скиллы/бафы тянутся выбранным набором |
| `stage_tables.py` | Перенос секций объектов в `table/*.ini` приёмника (+ `tables_update_existing` — режим починки существующих) |
| `stage_import.py` | Импорт ассетов донора в приёмник + запись в `table/imp.ini` (список созданного: `import_created.txt`) |
| `stage_code.py` | Триггеры/код: перенос `.j` с префиксацией функций (deploy_to, например LIA), GUI-пары `.lml+.txt`, осиротевшие `.txt` (текстовые триггеры), запись текущего каталога и манифеста деплоя; раскладка `code.folders` = `flat` (файлы в папку `<entry>` с префиксом) или `folders` (папки как в доноре) |
| `stage_code_cut.py` | Вырезание куска героя из монолит-скрипта донора (BFS по вызовам от точек входа) |
| `stage_globals.py` | Перенос globals/переменных донора (`variable.lml`, `udg_`), отчёт конфликтов имён/типов |
| `stage_geometry.py` | Декор/юниты в `war3map.doo` + высоты/текстуры `w3e` (экспериментально) |
| `stage_testspawn.py` | Генерация `TestSpawn.j` для перенесённых героев |
| `stage_verify.py` | Сверка результата по манифесту/таблицам: ошибок нет = 0; предупреждения не фейлят прогон |

## Обслуживание отдельной карты (не пайплайн переноса)

| Файл | За что отвечает |
| --- | --- |
| `stage_cleanup.py` | Чистка карты: скан --scan → подтверждение в GUI → удаление по JSON (без молчаливых удалений; бэкап перед удалением) |
| `stage_triggers.py` | Чистка триггеров: пустые папки, отключённые/закрытые триггеры, клоны (по подтверждённому JSON) |
| `stage_repair.py` | Починка `table/*.ini`: скобки, дубли секций, оборвы, битые `_parent` |
| `stage_rawconv.py` | Конверт обфусцированных равкодов в `.j` (0x... → 'RAWC', режим dec для десятичных литералов) |

## Важные вопросы/заметки к некому агенту

1. Запуски этапов: только через `py -3.14 -u ... <конфиг>`, по одному
   за раз; логи редиректом в `logs/`. Пример: `logs\_full_run5.log`.
2. Конфиг `transfer_config.json` после тестовых прогонов не сохранять
   изменённым (откат git-чекаутом) — он в гите.
3. push делает пользователь; агент готовит коммиты локально, CHANGELOG
   обновлять при каждой правке.
4. Кириллица/юникод: файлы только `encoding='utf-8'`; консоль с
   `[Console]::OutputEncoding = UTF8`.
5. Один пройденный полный прогон 22.10: ~13 сек wall (код 3.1 сек,
   verify 2.6 сек); верификация зелёная (0 ошибок, 6 предупрежен.
   IMP.INI).
6. Одноразовые скрипты прошлых сессий переехали 22.10 в `test/`; если
   создаёшь новый временный скрипт — или в `%TEMP%`, или сразу в `test/`,
   в гит не попадёт. Существующие скрипты не удалять (архив опыта).
7. Защита от дублирования при повторных прогонах (проверено живыми замерами
   22.10: двойные прогоны таблиц/mapping/globals — 0 изменений файлов):
   - stage_mapping: инкрементальный — прежние назначения неприкосновенны
     (KEY к паре карт, mapping_pair.json), новые объекты получают
     свободные ID из реестра занятых (target_id_registry);
   - stage_tables: дописывает только секции, которых НЕТ у приёмника
     (`not in tsec_ids`); правки донора в существующие — только по
     явной галочке tables_update_existing (пресет «Синхронизация
     существующих»);
   - stage_code: каталог и файлы деплоя чистятся по манифесту
     («поколения»), присвоенные ID и имена детерминированы
     (конфликтные значения — с префиксом LIA_ и переименованием ссылок);
   - stage_globals: при имени+типе совпавших переменных — skip + отчёт;
   - stage_verify: финальная сверка (дубли/битые ссылки/ассеты).
   Не менять эту логику «на глаз» — перед правками смотреть тесты
   в test/ (смёкика двойного прогона) иxED lessons.
